# 03 — Architecture

## Stack

| Layer | Choice | Notes |
|---|---|---|
| Framework | **Next.js (App Router) + TypeScript (strict)** | Use the newest Next.js version that `@opennextjs/cloudflare` officially supports at build time. Check the OpenNext docs first. |
| Hosting | **Cloudflare Workers** via **`@opennextjs/cloudflare`** | Free plan allows commercial use (needed for ads). Deploy with Wrangler. Not `next-on-pages` (deprecated edge-only path). |
| Database, auth, storage | **Supabase** (Postgres, Auth, Storage) | Free plan. `@supabase/ssr` for server/client helpers. |
| Styling | **Tailwind CSS** mapped to the CSS-variable tokens in `02-design-system.md` | Logical-property utilities only for direction. |
| i18n | **next-intl** | Locales `ar` (default) and `fr`. |
| Rich text | **Tiptap** (ProseMirror) | Admin only, loaded client-side with dynamic import. |
| Admin UI primitives | shadcn/ui (restyled) + Radix | Admin only. |
| Forms & validation | react-hook-form + **zod** | Same zod schemas validate server actions. |
| Charts | A small SVG chart library (e.g. visx or hand-rolled SVG) | Avoid heavy chart bundles. Admin only. |
| Tests | Vitest (unit), Playwright (e2e + screenshots) | |
| Package manager | pnpm | |

## Bundle size (important on Cloudflare free plan)

The Worker script is limited to **3 MiB (gzip) on the Workers Free plan** and 10 MiB on the Workers Paid plan ($5/month). Keep it under 3 MiB:

- Admin-only heavy libraries (Tiptap, charts, image compression, drag-and-drop) must be **client components loaded with `next/dynamic`** so they ship to the browser, not into the server bundle.
- Don't import the Supabase admin client or large SDKs into shared modules.
- After each phase, run the OpenNext build and record the Worker size in `docs/PROGRESS.md`. If it approaches 3 MiB, analyse with the bundle meta file and fix it. If it can't be fixed, stop and tell the owner that the $5 Workers Paid plan is needed.

## Environment variables

| Name | Where | Purpose |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | public | Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | public | Anon / publishable key (use whichever key type the project dashboard provides; Supabase introduced "publishable" and "secret" keys alongside the legacy anon/service_role keys) |
| `SUPABASE_SERVICE_ROLE_KEY` | **secret, server only** | Analytics ingestion, user invites, admin-only maintenance |
| `REVALIDATE_SECRET` | secret | Protects the on-demand revalidation endpoint |
| `SITE_URL` | public | Canonical origin, e.g. `https://elborj.tn` |
| `TRACKER_HMAC_SECRET` | secret | Signs the tracker payload token (see analytics doc) |

Provide `.env.example`. Secrets go to Cloudflare with `wrangler secret put` (document this in README).

Note: GA4 measurement ID, AdSense client ID and ads.txt content are **not** env vars; they live in `site_settings` so the owner can change them from the admin.

## Routing

- `/` → redirect (307) to `/ar`. Optionally honour a `NEXT_LOCALE` cookie if the reader picked French before.
- Public: `/{locale}/...` (see `05-public-site.md`).
- Admin: `/{locale}/admin/...`. Protected by middleware: no session → `/{locale}/admin/login`. Role checks on every server action, never only in the UI.
- Locale sets `<html lang dir>`: `ar` → `lang="ar" dir="rtl"`, `fr` → `lang="fr" dir="ltr"`.

## i18n model

Two separate concepts:

1. **Interface language** (`locale` in the URL): menus, labels, dates, buttons. All UI strings come from `messages/{locale}.json`. Admin-editable labels (site name, category names, menu labels, page titles) come from the database with `_ar` / `_fr` columns.
2. **Content language** (`articles.language`): each article is written in one language. Articles can be linked as translations through `translation_group_id`.

Rules:
- `/ar` lists Arabic articles; `/fr` lists French articles.
- Because French content will be thin at first, a setting `fr_include_arabic_content` (default `true`) lets French pages also list Arabic articles. Those items are rendered with `lang="ar" dir="rtl"` on the item itself and a small «AR» marker. The reverse setting `ar_include_french_content` defaults to `true` too (French items marked «FR»).
- An article URL lives under the locale of its language: an Arabic article is `/ar/article/...`. If someone opens it under `/fr/...`, redirect to the correct locale (or to the linked French translation if one exists).
- The language switch on an article page goes to the linked translation if one exists, else to the other locale's homepage.
- Categories, tags and formats are shared across languages, with bilingual names.

## Data access

- **Public pages** read through the anon key with RLS (only published content is visible). Use server components; no client-side Supabase calls on public pages.
- **Admin** uses the user's session (cookies via `@supabase/ssr`) so RLS applies to the logged-in role. Mutations are **server actions** that validate input with zod and re-check the role.
- **Service role** only in: analytics ingestion route, user invite/disable actions, scheduled maintenance endpoints. Isolate it in `src/lib/supabase/admin.ts` and import it only from server-only files (`import 'server-only'`).

## Caching and freshness

Goal: fast pages on free tiers, fresh within a minute.

- Public pages use ISR-style caching with `revalidate = 60` (seconds) as the baseline.
- On publish/update/unpublish in the admin, call `revalidateTag` / `revalidatePath` for: the article, its categories, the homepage, the author page, tags, the latest feed, sitemaps and RSS.
- Configure OpenNext's incremental cache and tag cache for Cloudflare as recommended in the OpenNext docs (R2 bucket for incremental cache; the tag-cache option they recommend). R2 has a free allowance; document any setup step in `supabase/APPLY.md`'s sibling `docs/DEPLOY.md`. If tag caching can't be made to work on the free plan, fall back to time-based revalidation only (60s) and log it.
- Scheduled articles: a `pg_cron` job flips due `scheduled` articles to `published` every minute (see database doc). They then appear within the 60s revalidation window. Optionally the job also calls `/api/revalidate` through `pg_net` with the secret; implement it if it works on the free plan, otherwise rely on time-based revalidation.
- Never cache admin pages or anything personalized.

## Images and media

- Uploads go to the Supabase Storage bucket `media` (public read).
- **Client-side processing before upload** (admin): convert to WebP, create variants at widths 480, 960, 1600 (and keep the original, max 2400px), strip EXIF except orientation. Use a small library (e.g. `browser-image-compression` or canvas). Store variant paths in `media.variants`.
- Public pages render `<img srcset>` from those variants with a custom `next/image` loader or plain `<img>`. **Do not use Cloudflare Images or Vercel image optimization** (cost). Supabase's own image transformation is a paid feature; don't depend on it.
- Admin must allow the owner to set a focal point by clicking on the image (stored `focal_x`, `focal_y` 0–1), used as `object-position`.

## Auth

- Staff only. Disable public sign-ups in Supabase Auth settings (document it in APPLY.md).
- Login: email + password, with "forgot password" via Supabase email. Magic link optional.
- Invites: admins invite users by email from the admin (service role `inviteUserByEmail`), choosing a role. A trigger creates the `profiles` row.
- First admin: the owner creates his user in the Supabase dashboard, then runs `bootstrap_admin.sql` with his email.
- Deactivating a user sets `profiles.is_active = false` and bans the auth user; their articles stay.

## Security

- RLS enabled on every table, with policies from the database doc.
- All mutations via server actions with zod validation and explicit role checks.
- Article HTML: generate `body_html` on the server from the Tiptap JSON with an allowlist renderer; sanitize again (e.g. `sanitize-html`) before storing. Embeds only from an allowlist of hosts (youtube.com, youtu.be, facebook.com, fb.watch, x.com, twitter.com, instagram.com) rendered by our own components, never raw iframes from input.
- Custom ad code (AdSense) is entered only by admins and only into ad-slot fields; render it in a sandboxed way where possible and never in article bodies.
- Security headers (CSP allowing Google ads/analytics domains, Supabase, our CDN; `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`). Document the CSP in `DECISIONS.md` because AdSense requires a fairly permissive policy.
- Rate-limit the tracker and contact endpoints (simple per-IP token bucket in the Worker plus validation; optionally a Cloudflare rate-limiting rule; document).

## Observability

- Log server errors with enough context to debug (route, user id, no personal data).
- An admin "system" page shows: Worker version/build time, Supabase DB size vs free-tier limit (500 MB), storage used vs limit (1 GB), number of raw analytics rows, last rollup run time and status. Get sizes through an admin-only SQL function.
